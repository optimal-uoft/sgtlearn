## Suspicions

### sgtlearn-base-py--sgtclassifier-init

Logical mistakes:
- The constructor coerces some hyperparameters (num_partitions, min_samples_leaf, the inner_* counts and thresholds, coordinate_descent_*) with int()/float() but leaves others as given (max_depth, max_leaf_nodes, pairwise_*, branching_penalty, tao_*). This is inconsistent. It also goes against the scikit-learn convention that __init__ stores parameters exactly as passed. With int(), a non-integral value such as 2.7 is silently cut down to 2. Numpy scalars or strings are converted to a different object, so get_params() no longer returns what the user passed, which can break clone().
- Fitted attributes (classes_, n_classes_, n_outputs_, n_features_in_, feature_names_in_) are created at construction time. n_outputs_ is even set to 1. Scikit-learn's check_is_fitted looks for attributes ending in an underscore, so an unfitted estimator can be reported as fitted, and the "not fitted" error is never raised before fit.
- Because only some parameters are coerced, a bad value for a coerced parameter (for example num_partitions="abc" or None) raises TypeError/ValueError at construction. The same bad value for an uncoerced parameter only fails later in fit.

Robustness omissions:
- There is no clear rule for when validation happens. Under the scikit-learn contract, range and type checks (criterion in the supported set, num_partitions >= 2, min_samples_leaf >= 1, min_impurity_decrease >= 0, a valid max_features spec, pairwise_candidates in range, tao_pair_scale validity, tao_n_runs >= 1, and so on) should all be done in fit, not scattered between the constructor and fit.
- Nothing guards against bool being accepted as an int, or against a float that is not a whole number being truncated without warning.

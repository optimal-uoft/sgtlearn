## Suspicions

### sgtlearn-weights-py--effective-sample-weight-classification

Logical mistakes: No happy-path error found. The weights for each output are multiplied together, then multiplied by sample_weight, which matches sklearn's compute_sample_weight for multi-output targets. Two points are worth noting:
(a) A str is itself a Sequence. So a string class_weight (for example "balanced") is not rejected as the wrong type. It is treated as a sequence of characters, which gives either a confusing length-mismatch ValueError or, when the string length equals n_outputs, a failure deeper in the code. Strings should be rejected with TypeError.
(b) The single-output detection for classes_ depends on its container type. For single-output data, a plain Python list of labels such as [0, 1, 2] is read as a list of per-output class arrays, so it raises a ValueError instead of being accepted as one output's classes.
Robustness omissions:
- y_enc is cast to int64 without checking. Non-integer values (such as 0.7) are truncated silently instead of being rejected.
- When class_weight is a sequence, its elements are never checked to be mappings. A wrong element fails later with an unclear error instead of a clear TypeError.
- Because sample_weight is flattened, a 2-D array with n elements (for example shape (n, 1) or (1, n)) is accepted. A strict version would require a 1-D array of length n_samples.
- The result is stored as float32, which loses precision against the float64 inputs. This appears to be a deliberate choice for downstream consumers, but it should be documented.
- Empty input (n_samples == 0) should give an empty float32 array. Validating y values against classes_ and validating the weight values is left to the helper functions and should be part of the contract.
